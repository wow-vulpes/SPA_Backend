# Требования MVP

Стек: Java 21, Spring Boot, Maven, PostgreSQL/Hibernate, Lombok, MapStruct,
JUnit и Mockito. REST API без интерфейса, LLM, автоматического размещения
заказов и отдельного бюджетного модуля.

## Инфраструктура

- TECH-01: фиксированные совместимые зависимости и Maven Wrapper.
- RUN-01: запуск приложения и PostgreSQL через Docker Compose; полный demo-набор на шаге 8.
- CFG-01: конфигурация через переменные окружения, без секретов в Git.
- QA-01: unit-тесты правил, интеграционные тесты на PostgreSQL, проверяемая сборка и CI.
- DOC-01: README описывает запуск, тесты, конфигурацию и ограничения.
- TIME-01: бизнес-зона Europe/Moscow по умолчанию и внедряемый Clock.

## Учётная модель (шаг 2)

- DATA-01: товары с уникальным SKU и объекты с уникальным кодом; позиция — уникальная пара SKU/объект с датой регистрации.
- DATA-02: партия относится к позиции; хранит номер, дату поступления, срок годности, цену в RUB и накладную. Номер партии уникален внутри позиции.
- DATA-03: движение имеет дату, позицию, тип, количество и глобально уникальный номер документа; типы RECEIPT, CONSUME, WRITEOFF, RETURN, CORRECTION.
- DATA-04: количество положительно для всех типов, кроме CORRECTION: у неё ненулевое знаковое значение. Цена неотрицательна. Пустые ключи/номера и NaN запрещены.
- DATA-05: распределение связывает движение и партию одной позиции; пара движение/партия уникальна, изменение количества ненулевое. Ссылочная целостность запрещает удаление используемых записей.
- DATA-06: физический остаток — сумма знаковых изменений партий без повторного сложения заголовков движений. Отдельного изменяемого остатка нет. Пустая позиция/партия имеет нулевой остаток.
- DATA-07: доступный остаток исключает партии со сроком меньше бизнес-даты; в день окончания срока партия ещё доступна. Просрочка остаётся в физическом остатке до списания.
- DATA-08: точность количества — до 6 знаков после запятой, цены — до 4; Java BigDecimal и PostgreSQL numeric(19,6)/(19,4). Проверка лишней точности внешнего ввода — шаг 3.
- DATA-09: позиция предоставляет транзакционную блокировку даже без партий. Запись движения и распределений должна быть атомарной; поведение репозиториев при rollback проверяется отдельно.
- DATA-10: схема изменяется Flyway; опубликованная V1 сохраняется. Проверяются чистая БД, обновление V1 → V2, повторный запуск и Hibernate validate.

## Последующие функции

- MOV-01: POST /api/movements проводит пять типов операций и возвращает ID и остаток.
- MOV-02: consume распределяется по FEFO (срок, дата поступления, ID), исключает просрочку; writeoff списывает указанную партию, return возвращает в исходную партию, correction меняет её остаток.
- MOV-03: запрет отрицательного остатка, будущей даты и даты раньше последней операции позиции; согласованность количества заголовка и распределений, их знаков, атомарность и защита от одновременного расхода.
- MOV-04: неизвестная ссылка — 404; повтор документа — 409; семантическая ошибка/нехватка — 422 с доступным количеством; повреждённый JSON — 400.
- HIST-01: GET /api/movements с фильтрами SKU, объект, тип, период и limit/offset/total.
- STOCK-01: GET /api/stock: физический/доступный остаток, средний consume за предыдущие 90 полных дней, запас в днях, ближайший срок.
- STOCK-02: GET /api/stock/{sku}: остатки по объектам и партиям, сроки, цены, накладные.
- FORECAST-01: POST /api/forecast: календарный горизонт с текущей даты, средний расход, страховой запас, точка заказа, открытые поставки, закупка и стоимость, даты, explanation и warnings.
- FORECAST-02: прогноз = средний расход × дни; точка заказа = средний расход × (срок поставки + страховые дни); потребность = max(0, прогноз + страховой запас − доступный остаток − поставки в горизонте). Ненулевая закупка = ceil(max(потребность, MOQ)/упаковка) × упаковка.
- FORECAST-03: цена последнего поступления на объекте; отсутствующая цена и неопределимые даты — null с объяснением. Нулевой расход не вызывает деления на ноль. Истечение партий и даты поставок учитываются в рисках и датах; ограничения агрегатной формулы явно описываются.
- ALERT-01: GET /api/alerts: дефицит, истечение/просрочка, отсутствие движения; важность и исходные показатели. Начальные пороги 30 и 90 дней настраиваются.

Межстрочные бизнес-инварианты MOV-02/MOV-03 реализуются сервисом шага 3.
Наличие persistence-модели само по себе не означает готовность проведения
движений: репозитории не являются публичным API или завершённым сервисом.
