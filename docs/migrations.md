# Единая начальная миграция

`V1__inventory_model.sql` создаёт шесть таблиц, ограничения и индексы
в чистой базе. Ранние версии использовали пустую V1 и предметную V2;
текущий набор не предназначен для автоматического обновления той схемы.

Проверки: чистое применение одной V1, повторный migrate без выполнения SQL,
Flyway validate и Hibernate validate. Старая V2 не должна оставаться в
скомпилированных ресурсах: после обновления выполните `./mvnw clean verify`.

## Если приложение уже запускалось со старой V1/V2

В старой базе остались версии и контрольные суммы прежних файлов. Простая
пересборка приложения этого не исправит; Flyway остановит запуск при проверке.
Автоматически удалять историю Flyway или выполнять repair проект не будет.

Для новой локальной базы можно использовать отдельный Compose-проект:

```bash
docker compose stop
docker compose -p spa-v1 up --build
```

Первая команда освобождает порт старого приложения, сохраняя его данные.
Вторая создаёт отдельный том `spa-v1_spa-postgres-data`; старая база остаётся
в прежнем томе. Последующие команды для нового окружения выполняйте с тем же
`-p spa-v1`. Это новая пустая база, прежние записи автоматически не переносятся.
Если нужны старые данные, требуется отдельный перенос с резервной копией;
автоматического переноса в приложении нет.

В дальнейшем применённые миграции не редактируются: изменения схемы идут
новыми V2, V3 и так далее.
