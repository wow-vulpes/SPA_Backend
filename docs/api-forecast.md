# Прогноз закупки

`POST /api/forecast`, Content-Type: application/json, HTTP 200 при успехе.
Это расчёт для одного SKU/объекта; он не создаёт заказ, движение, позицию
или запись истории расчётов. Справочники товара и объекта должны существовать.

```json
{
  "sku": "OIL",
  "location": "SPA",
  "horizon_months": 1,
  "lead_time_days": 3,
  "safety_days": 2,
  "minimum_order_quantity": 0,
  "pack_size": 3,
  "open_deliveries": []
}
```

| Поле | Правило |
| --- | --- |
| sku, location | Обязательные ключи, 1–64 символа, обрезаются краевые пробелы, регистр учитывается |
| horizon_months | 1, 3, 6 или 12 календарных месяцев от сегодня |
| lead_time_days | Целое число 0–365, срок новой поставки |
| safety_days | Целое число 0–365, страховой запас в днях расхода |
| minimum_order_quantity | Число >= 0, минимальный заказ (MOQ) |
| pack_size | Число > 0, размер упаковки в единицах товара |
| open_deliveries | Необязательный список (null/отсутствие равносильны []), максимум 1000 элементов |

Элемент open_deliveries: `{"expected_date":"2026-10-05","quantity":10}`.
Дата обязательна, не раньше бизнес-даты сегодня; количество строго положительно.
Количество, MOQ, упаковка: до 13 целых и 6 дробных цифр. Дробные значения
целочисленных полей отклоняются. Неверные поля/период/даты — 422, повреждённый
JSON — 400, неизвестный SKU/объект — 404 в общем формате ошибок API.
Нулевой символ в строках запрещён; даты ограничены годами 0001–9999.

Сроки, MOQ, упаковка и открытые поставки — параметры конкретного расчёта,
поскольку реестр поставщиков и открытых заказов ещё не реализован. Они не
сохраняются: для повторного расчёта их нужно передать снова. Просроченному
ожидаемому заказу нужно указать актуальную ожидаемую дату.

## Формулы и точность

Сегодня определяется один раз через Clock/APP_TIME_ZONE. Горизонт —
[сегодня; сегодня.plusMonths(horizon_months)), правая граница исключена.
Например, 31 января + 1 месяц — 28/29 февраля, а не фиксированные 30 дней.
Исторический расход — CONSUME за предыдущие 90 полных дней, сегодня исключено.

```text
average = historical_consumption / 90
forecast_demand = average × horizon_days
safety_stock = average × safety_days
reorder_point = average × (lead_time_days + safety_days)
incoming_quantity = сумма поставок с today <= expected_date < period_end_exclusive
net_requirement = max(0, forecast_demand + safety_stock - available_stock - incoming_quantity)
recommended_quantity = 0, если net_requirement = 0
recommended_quantity = ceil(max(net_requirement, MOQ) / pack_size) × pack_size, иначе
estimated_cost = recommended_quantity × unit_price
```

Расчёт объёма сохраняет точный делитель 90 до округления к упаковке. Округлённое
среднее не используется для принятия решения: минимальный расход не теряется.
Выводные количества округляются HALF_UP до 6 знаков, стоимость — до 2.
При очень малом расходе выводное среднее/потребность могут округлиться до 0,
хотя точный расчёт ещё рекомендует минимальную упаковку.

Цена в RUB берётся из последнего RECEIPT этого SKU/объекта: operation_date DESC,
id DESC. Повторное поступление в старую партию считается новым событием;
дата первого поступления партии не определяет «последнюю» цену. Возвраты,
корректировки и поступления на другом объекте её не меняют. Нулевая цена
допустима. При отсутствии RECEIPT unit_price и estimated_cost равны null.

## Календарные риски и даты

Отдельная симуляция проходит каждый день горизонта. В начале дня исключаются
остатки партий с expires_on < текущего дня и поступают ожидаемые поставки.
Затем списывается средний спрос по FEFO. В день истечения партия ещё доступна.
Симуляция не включает рекомендованный новый заказ, не переносит неудовлетворённый
спрос на будущие дни и не меняет реальный склад.

- first_shortage_date — первый день, когда не удастся покрыть весь дневной спрос;
  null означает, что дефицит не найден внутри горизонта, а не бесконечную обеспеченность.
- recommended_order_date — первая дата с запасом <= reorder_point, но не позже
  first_shortage_date − lead_time_days; прошедшая дата заменяется на сегодня.
  При recommended_quantity=0 дата заказа равна null. Если дату нельзя найти
  в горизонте, она также null с предупреждением.
- expected_arrival_date — дата рекомендуемого заказа + срок поставки, либо null.
- projected_expired_quantity — количество текущих непросроченных партий,
  которое истечёт до использования внутри горизонта. Уже просроченное сегодня
  сюда не входит: оно исключено из available_stock и отражено предупреждением.
- projected_unmet_demand — сумма неудовлетворённого спроса по дням.

Общая формула вычитает весь доступный запас и поставки в горизонте. Она сама
не увеличивает закупку из-за будущей просрочки и не разделяет закупку на даты.
Поэтому нулевой рекомендованный объём может сопровождаться календарным дефицитом:
такой результат получает AGGREGATE_PLAN_INSUFFICIENT и требует пересмотра плана.
Это прозрачная базовая модель, а не оптимизатор графика закупок.

Для ожидаемых поставок срок годности неизвестен; симуляция предполагает,
что они годны до конца горизонта. Влияние этого допущения явно отмечается.
Не учитываются сезонность, плановая загрузка SPA, резервирование, цены поставщиков,
изменение стоимости и бюджетный лимит. Открытые поставки после горизонта исключены.

## Ответ

Ответ содержит sku, name, unit, location и следующие поля контракта:

| Поле | Содержание |
| --- | --- |
| period | Объект from/to/days; from и to включительны |
| avg_daily_consumption | Средний расход за предыдущие 90 полных дней |
| forecast_demand, current_stock, incoming_qty | Прогноз спроса, физический остаток, поставки в горизонте |
| safety_stock, reorder_point, recommended_purchase_qty | Страховой запас, точка заказа и объём закупки |
| unit_price, estimated_cost | Цена последнего поступления и стоимость |
| recommended_order_date, stockout_date | Даты заказа и первого календарного дефицита, либо null |
| explanation | Объект data_used (исходные данные), formulas, assumptions и as_of |
| warnings | Массив объектов level/message/code; level = info или warning |

Дополнительно возвращаются available_stock, historical_consumption,
consumption_from/consumption_to, as_of, period_end_exclusive, horizon_days,
net_requirement, expected_arrival_date, projected_expired_quantity,
projected_unmet_demand, currency="RUB". В отличие от period.to, поле
period_end_exclusive обозначает исключённую правую границу.

Для совместимости сохранены прежние числовые имена: average_daily_consumption
= avg_daily_consumption, incoming_quantity = incoming_qty, recommended_quantity
= recommended_purchase_qty, first_shortage_date = stockout_date. Все пары
формируются из одного значения. Поле explanation имеет структуру объекта;
клиентам прежнего массива строк нужно использовать вложенные списки.

Пример значений для 29.09.2026: 90 единиц расхода в истории, доступно 12,
цена 2.125, остальные параметры из примера запроса. Горизонт — 30 дней,
прогноз 30, страховой запас 2, точка заказа 5, потребность 20, закупка 21,
стоимость 44.63 RUB. При годности всех партий за горизонтом и без поставок
первый дефицит — 11.10.2026, заказ — 06.10.2026, прибытие — 09.10.2026.

| Код предупреждения | Причина |
| --- | --- |
| CONSTANT_DEMAND_MODEL | Постоянный средний расход без сезонности; всегда раскрывает ограничение модели |
| LIMITED_HISTORY | Позиция новая или ещё не создана; делитель всё равно 90 |
| NO_CONSUMPTION | Нет CONSUME за окно, закупка по модели 0, дата заказа null |
| PRICE_UNAVAILABLE | Нет подходящего поступления с ценой |
| EXPIRED_STOCK | Уже просроченный запас исключён из доступного |
| DELIVERY_ASSUMPTION | Поставки из запроса считаются своевременными и годными до конца периода |
| DELIVERY_OUTSIDE_HORIZON | Есть неучтённые поставки за горизонтом |
| EXPIRY_WITHIN_HORIZON | Симуляция выявила истечение неиспользованного остатка |
| PROJECTED_SHORTAGE | Симуляция выявила нехватку |
| AGGREGATE_PLAN_INSUFFICIENT | Формула даёт 0 закупки, но календарь выявляет дефицит |
| ORDER_DATE_UNAVAILABLE | Для положительной закупки нет определимой даты в горизонте |
| LEAD_TIME_RISK | Даже заказ сегодня не успевает к первому дефициту |

Чтение остатков, истории и цены использует один снимок REPEATABLE_READ.
Известный товар на известном объекте без позиции рассчитывается с нулевыми
остатком/расходом и неизвестной ценой; новая позиция при этом не создаётся.
Пересчёт — повтор того же POST с другими параметрами.
