# API предупреждений

`GET /api/alerts` возвращает актуальные предупреждения без записи в БД.
Бизнес-дата определяется один раз из Clock и APP_TIME_ZONE. Подтверждения,
сохранения истории предупреждений и фоновой рассылки пока нет.

```bash
curl 'http://localhost:8080/api/alerts?sku=OIL&location=SPA&limit=50&offset=0'
```

## Правила

| type | Условие | severity |
| --- | --- | --- |
| SHORTAGE | Расход CONSUME за предыдущие 90 полных дней > 0; доступный остаток × 90 < расход × lead_time_days | CRITICAL при нулевом доступном остатке, иначе WARNING |
| EXPIRED | Остаток партии > 0, expires_on < as_of | CRITICAL |
| EXPIRING | Остаток партии > 0, as_of ≤ expires_on ≤ as_of + expiry_days | WARNING |
| NO_MOVEMENT | Физический остаток > 0, последняя операция любого типа ≤ as_of − inactivity_days | INFO |

SHORTAGE и NO_MOVEMENT — одна строка на SKU/объект, сроки — одна строка
на партию. Предупреждения могут сосуществовать. EXPIRED и EXPIRING
взаимоисключающие для одной партии. В день окончания срока партия ещё
доступна. Полностью использованные партии и пустые позиции не вызывают
предупреждений о сроках/отсутствии движения. У корректного положительного
остатка всегда есть движение; дата регистрации позиции его не заменяет.

Для дефицита используется точное сравнение до округления. Равенство запасу
на lead_time_days не создаёт SHORTAGE. Доступный остаток исключает просрочку;
физический её включает. Количество суммируется по распределениям, расход —
отдельно по заголовкам CONSUME, без умножения на количество партий.

Средний расход = CONSUME за [as_of−90; as_of) / 90, отображается с 6 знаками.
days_of_stock = доступный остаток × 90 / исходный расход, с 2 знаками,
HALF_UP. При нулевом расходе days_of_stock = null. Очень маленький положительный
расход может округлиться до нуля в ответе, но не исчезает из правила SHORTAGE.
historical_consumption позволяет проверить такой случай.

NO_MOVEMENT означает отсутствие **любых** операций, не только потребления.
Приход, расход, возврат, списание и коррекция обновляют last_movement_date.
INFO не означает автоматического решения о списании: сотрудник проверяет причину.

## Фильтры и пагинация

- `sku`, `location`: необязательные точные, регистрозависимые значения;
  внешние пробелы удаляются, длина после удаления 1–64 символа.
- `limit`: целое 1–100, по умолчанию 50; `offset`: 0–2147483647, по умолчанию 0.
- `lead_time_days`: необязательный срок поставки 0–3650 дней для выбранных
  позиций. Без параметра применяется срок из конфигурации. При нуле SHORTAGE
  не возникает: запас не может быть меньше нулевого срока поставки.
- Неверный/пустой явно переданный параметр — 422, code `INVALID_ALERT_FILTER`.
- Нулевой символ в строковом фильтре — 422, code `INVALID_FIELD`.
- Неизвестные SKU/объект и отсутствие предупреждений — 200, items=[], total=0.
- total — число предупреждений после фильтров, до пагинации. Даже если offset
  выходит за конец, total сохраняется.
- Порядок: CRITICAL → WARNING → INFO, затем sku, location, type, batch_id
  по возрастанию (null первым). Пагинация применяется к предупреждениям,
  а не к позициям. Между разными запросами журнал может измениться.

Count и страница выполняются в одной read-only транзакции REPEATABLE_READ;
агрегирование, фильтрация и пагинация идут в PostgreSQL, без загрузки всего
склада в Java и без запроса на каждую партию.

## Ответ

Верхний уровень: `as_of`, `consumption_from`, `consumption_to` (последняя дата
включительно), `lead_time_days`, `expiry_days`, `inactivity_days`, `items`,
`total`, `limit`, `offset`.
`shortage_days` сохранено как совместимый псевдоним lead_time_days.

Каждый элемент items содержит:

- `sku`, `location`, `unit`, `type`, `severity`, русское `message`;
- `current_stock`, `available_stock`, `historical_consumption`,
  `average_daily_consumption`, `days_of_stock` — показатели всей позиции;
- `last_movement_date` — дата последней операции позиции;
- `batch_id`, `batch_number`, `batch_quantity`, `expires_on` — сведения о
  конкретной партии для EXPIRED/EXPIRING, иначе null.

Типы и важность — стабильные коды в верхнем регистре; текст предназначен
для человека. Количества выражаются в unit товара, не в упаковках поставщика.

## Настройки

| Переменная окружения | Spring property | По умолчанию | Диапазон |
| --- | --- | --- | --- |
| APP_ALERTS_LEAD_TIME_DAYS | app.alerts.lead-time-days | 30 | 0–3650 |
| APP_ALERTS_EXPIRY_DAYS | app.alerts.expiry-days | 30 | 0–3650 |
| APP_ALERTS_INACTIVITY_DAYS | app.alerts.inactivity-days | 90 | 1–3650 |

Настройки передаются и в Compose, и при запуске из IDE. Невалидное значение
останавливает запуск с ошибкой конфигурации. APP_ALERTS_SHORTAGE_DAYS остаётся
резервным значением при отсутствии APP_ALERTS_LEAD_TIME_DAYS. Старое прямое
Spring-свойство app.alerts.shortage-days заменено на app.alerts.lead-time-days.
Параметр запроса имеет приоритет над конфигурацией; его ошибки возвращают 422.
expiry_days=0 оставляет
просрочку и партии, истекающие сегодня. Верхняя граница 3650 — защитный
предел десяти лет для ошибочного ввода, не бизнес-прогноз. После изменения
настроек приложение нужно перезапустить (Compose — пересоздать контейнер).

## Ограничения

Это проверка текущего состояния. SHORTAGE использует постоянный средний
расход без сезонности, будущих поставок и будущего истечения
партий. EXPIRED/EXPIRING выводятся независимо от того, успеет ли партия
израсходоваться. Отдельного справочника сроков поставки по товарам нет:
передавайте фактический срок через lead_time_days при фильтрации SKU/объекта.
Для календарной FEFO-проверки и поставок используйте
[POST /api/forecast](api-forecast.md). При неполной истории средний всё равно
делится на 90; отсутствие SHORTAGE при нулевом расходе не гарантирует
достаточность запасов. Предупреждения о ценах и аномалиях расхода в этот шаг
не входят. Лимит ответа ограничивает передачу данных, но агрегирование
большого журнала требует отдельной проверки производительности.
