# Учётная модель

| Таблица | Ключ и назначение |
| --- | --- |
| product | sku; наименование и единица измерения |
| location | code; объект SPA |
| inventory_position | id; уникальная пара sku/location_code, registered_on |
| batch | id; партия позиции, received_on, expires_on, unit_price, invoice_number |
| movement | id; заголовок операции, operation_date/type, quantity, document_number |
| movement_allocation | id; movement_id/batch_id/position_id, quantity_delta |

Одна позиция содержит несколько партий и движений. Одно движение может иметь
несколько распределений. Составные внешние ключи `(movement_id, position_id)`
и `(batch_id, position_id)` гарантируют принадлежность одной позиции.
Удаления по каскаду нет. Справочники и журнал не предоставляют HTTP CRUD.

Связи в Java представлены идентификаторами; PostgreSQL отвечает за ссылочную
целостность. Entities не имеют публичных сеттеров. Изменяемые количества
остатка отсутствуют и в entities, и в таблицах.

Пример: поступления +5 и +7 в две партии, затем расход 6 с распределениями
−5 и −1. Остаток равен 6. Количество 6 из заголовка расхода повторно не
вычитается: источник расчёта — только распределения.

`StockRepository` предоставляет:

- `physicalQuantity(positionId)` — сумма всех изменений позиции;
- `availableQuantity(positionId, businessDate)` — та же сумма для непросроченных партий;
- `batchBalances(positionId)` — все партии, включая пустые и просроченные,
  с остатком, ценой и накладной, в порядке срока, даты поступления и ID.

Это текущий журнал, а не исторический срез. `businessDate` фильтрует срок
годности, но не отменяет движения после этой даты. Репозиторий возвращает 0
для отсутствующего ID; будущий сервис проверяет существование позиции/SKU
перед формированием HTTP-ответа.

Количество — numeric(19,6), цена — numeric(19,4) в RUB. PostgreSQL округляет
избыточный scale; API отклоняет такой ввод до записи.
Сроки и даты — LocalDate/date. Идентификаторы чувствительны к регистру.

Индексы поддерживают выборку позиции по SKU/объекту, FEFO-порядок партий,
движения по позиции/дате и суммирование распределений. Уникальные ограничения
уже создают свои индексы; дополнительные дубли не добавлены.

`findByIdForUpdate` и `findForUpdate` требуют открытой транзакции. Блокировка
удерживается до её завершения. MovementService сначала выполняет INSERT ON
CONFLICT DO NOTHING для позиции, затем блокирует её по SKU/объекту. Внутри
одной READ_COMMITTED транзакции проверяет дату, рассчитывает распределения
и записывает движение. Уникальность документа защищает также разные позиции.
FEFO и запрет отрицательного остатка проверены через HTTP, включая конкуренцию.

V1 остаётся неизменной. V2 добавляет шесть таблиц, ограничения и индексы;
данные пользователя и demo-набор не изменяет. Тесты поднимают собственные
временные PostgreSQL-контейнеры с детерминированными датами и фикстурами.
