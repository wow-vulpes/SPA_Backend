# SPA Inventory & Procurement Assistant

REST API для складского учёта и планирования закупок сети SPA-салонов.
Приложение регистрирует движения по партиям, рассчитывает остатки и потребность
в закупке, предупреждает о дефиците и сроках годности.

**Стек:** Java 21, Spring Boot 4.0.8, Maven, PostgreSQL 17.11, Hibernate,
Flyway, Lombok, MapStruct, JUnit, Mockito и Testcontainers.

## Запуск

Нужен Docker с Compose. Из корня репозитория:

```bash
docker compose up
```

Первый запуск собирает приложение и скачивает зависимости. После запуска
проверить готовность можно в другом терминале:

```bash
curl --fail http://localhost:8080/actuator/health/readiness
```

Ответ `{"status":"UP"}` означает, что приложение готово и начальные данные
загружены. API доступен на `http://localhost:8080`. PostgreSQL наружу не публикуется.
После изменения кода используйте `docker compose up --build`.
Команда `docker compose down` останавливает контейнеры, сохраняя данные в томе.

Flyway автоматически создаёт схему. В пустую базу загружается синтетический
набор: 4 товара, 2 объекта, 6 партий и 101 движение. Повторный запуск сохраняет
существующие данные. Даты набора рассчитываются при первой загрузке и затем
не сдвигаются.

## Быстрая проверка API

Остатки, партии, история и предупреждения:

```bash
curl 'http://localhost:8080/api/stock?sku=DEMO-OIL&location=DEMO-CENTER'
curl 'http://localhost:8080/api/stock/DEMO-OIL'
curl 'http://localhost:8080/api/movements?sku=DEMO-OIL&type=consume&limit=5'
curl 'http://localhost:8080/api/alerts?location=DEMO-CENTER'
```

Прогноз на месяц:

```bash
curl -X POST http://localhost:8080/api/forecast \
  -H 'Content-Type: application/json' \
  -d '{
    "sku": "DEMO-OIL",
    "location": "DEMO-CENTER",
    "horizon_months": 1,
    "lead_time_days": 3,
    "safety_days": 5,
    "minimum_order_quantity": 0,
    "pack_size": 10,
    "open_deliveries": []
  }'
```

В день первой загрузки неизменённого набора для этой позиции доступны 20 единиц,
средний расход равен 1 единице в день. Пример прогноза рекомендует 20 единиц
на сумму 5000 RUB. Ответ содержит исходные показатели, формулы, допущения,
даты заказа и дефицита, а также предупреждения. Расчёт не создаёт заказ.

## Контракт API

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/movements` | Запись движения; ответ 201 с ID, остатками и распределением по партиям |
| `GET /api/movements` | История; фильтры `sku`, `location`, `type`, `date_from`, `date_to` |
| `GET /api/stock` | Остатки, средний расход, дни запаса и ближайший срок; фильтры `sku`, `location` |
| `GET /api/stock/{sku}` | Товар, объекты и партии с остатками, сроками, ценами и накладными |
| `POST /api/forecast` | Прогноз закупки для товара на объекте |
| `GET /api/alerts` | Дефицит, просрочка, приближение срока, отсутствие движения; фильтры `sku`, `location`, `lead_time_days` |

Списки используют `limit` (1–100, по умолчанию 50) и `offset` (от 0);
ответ содержит `items`, `total`, `limit`, `offset`. Даты фильтров истории
включительны. История сортируется по дате операции и ID по убыванию.
Неизвестный код в фильтре даёт пустой список; неизвестный товар в пути — 404.

### Регистрация движений

Общие поля: `sku`, `location`, `operation_date`, `type`, `quantity`,
`document_number`. Номер документа уникален для всего журнала.

| Тип | Партия | Количество |
| --- | --- | --- |
| `receipt` | `batch` с реквизитами новой партии либо `batch_id` существующей | Положительное |
| `consume` | Автоматический выбор FEFO, без `batch` и `batch_id` | Положительное |
| `writeoff` | `batch_id` | Положительное |
| `return` | `batch_id` исходной партии | Положительное |
| `correction` | `batch_id` | Ненулевое, со знаком |

Пример тела поступления (дату операции задайте не позже текущей и не раньше
последней операции этой позиции):

```json
{
  "sku": "DEMO-OIL",
  "location": "DEMO-CENTER",
  "operation_date": "2026-09-30",
  "type": "receipt",
  "quantity": 10,
  "document_number": "RECEIPT-EXAMPLE-001",
  "batch": {
    "number": "B-EXAMPLE-001",
    "expires_on": "2027-09-30",
    "unit_price": 250,
    "invoice_number": "INV-EXAMPLE-001"
  }
}
```

SKU и код объекта — до 64 символов; номера документа, партии и накладной —
до 128. Количество допускает 13 целых и 6 дробных цифр, цена — 15 и 4.
Цена неотрицательна. JSON-даты принимаются только строкой `YYYY-MM-DD`
с годом 0001–9999. Лишняя точность и дробные ID отклоняются.

Ошибки: **400** — повреждённый JSON или повторяющиеся ключи; **404** —
неизвестная ссылка; **409** — повтор документа или конфликт блокировки;
**422** — неверные значения, хронология или нехватка остатка.
Ответ содержит `status`, `code`, `message`, `violations`; при нехватке также
`available_quantity`. Повтор документа возвращает 409, а не повторяет результат.

### Прогноз и предупреждения

В прогнозе обязательны поля из примера, кроме `open_deliveries`.
`horizon_months` принимает 1, 3, 6 или 12; `lead_time_days` и `safety_days` —
целые 0–365; минимальный заказ неотрицателен, упаковка строго положительна.
Ожидаемая поставка имеет вид `{"expected_date":"2026-10-05","quantity":10}`:
дата не раньше текущей, количество положительное, максимум 1000 поставок.

При среднем расходе `a` и числе дней горизонта `d`:

```text
a = расход consume за предыдущие 90 полных дней / 90
спрос = a × d
страховой запас = a × safety_days
точка заказа = a × (lead_time_days + safety_days)
потребность = max(0, спрос + страховой запас − доступный остаток − поставки в горизонте)
закупка = 0 при нулевой потребности, иначе ceil(max(потребность, MOQ) / упаковка) × упаковка
стоимость = закупка × цена последнего поступления на выбранном объекте
```

Горизонт — календарные месяцы от сегодня; текущий день не входит в историю
расхода. Промежуточное среднее не округляется перед расчётом закупки.
При отсутствии цены стоимость равна `null`; при отсутствии расхода модель
даёт нулевую потребность и предупреждение. Неполная история также делится на 90.

Дневная симуляция отдельно учитывает FEFO, истечение партий и даты поставок.
Она определяет первый дефицит и риски; формула общего объёма не компенсирует
будущую просрочку. Поэтому даже при нулевой закупке возможен календарный дефицит:
в ответе он явно отмечается. Для ожидаемых поставок предполагается годность
до конца горизонта. Это базовый прогноз постоянного спроса, без сезонности.

Предупреждения: `SHORTAGE` — доступного запаса меньше срока поставки;
`EXPIRED` и `EXPIRING` — сроки партий; `NO_MOVEMENT` — отсутствие любых движений.
Они содержат важность и исходные показатели. Для проверки дефицита срок поставки
можно передать в `GET /api/alerts?lead_time_days=14` (0–3650 дней).

## Архитектура

Один Maven-модуль: контроллеры принимают DTO, сервисы выполняют бизнес-операции
и задают транзакции, репозитории работают с PostgreSQL. `ForecastCalculator`,
`StockMetrics` и `FefoAllocator` содержат расчёты, тестируемые без HTTP и БД.

Схема состоит из `product`, `location`, `inventory_position`, `batch`,
`movement` и `movement_allocation`. Остаток вычисляется из распределений
движений; отдельного изменяемого поля остатка нет. Физический остаток включает
просрочку, доступный её исключает. FEFO выбирает партию по сроку, дате
поступления и ID. В день истечения партия ещё доступна.

Запись блокирует позицию до завершения транзакции, предотвращая конкурентное
списание сверх остатка. Движение и распределения сохраняются атомарно.
Чтение связанных показателей использует один снимок `REPEATABLE_READ`.
Flyway управляет схемой, Hibernate проверяет её через `ddl-auto=validate`.
Бизнес-дата определяется через `Clock` в настроенном часовом поясе.

Spring Boot обеспечивает REST, валидацию и транзакции; PostgreSQL — точные
числа, ограничения и блокировки. Lombok сокращает шаблонный код, MapStruct
проверяет преобразования DTO при компиляции. Maven Wrapper фиксирует Maven,
а Testcontainers позволяет проверять поведение на настоящей PostgreSQL.

## Конфигурация

Для Compose можно скопировать `.env.example` в `.env` и изменить значения.
`.env` не хранится в Git.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `APP_PORT` | Порт API на хосте | 8080 |
| `APP_DEMO_ENABLED` | Начальные данные только для пустой БД | true в Compose; false вне Compose |
| `APP_TIME_ZONE` | Бизнес-часовой пояс | Europe/Moscow |
| `APP_ALERTS_LEAD_TIME_DAYS` | Срок поставки для предупреждений | 30 |
| `APP_ALERTS_EXPIRY_DAYS` | Порог приближения срока годности | 30 |
| `APP_ALERTS_INACTIVITY_DAYS` | Порог отсутствия движений | 90 |
| `DB_NAME` | Имя базы в Compose | spa |
| `DB_USER`, `DB_PASSWORD` | Доступ к локальной демонстрационной БД | spa / spa |
| `DB_URL` | JDBC URL вне Compose | jdbc:postgresql://localhost:5432/spa |

В Compose JDBC URL формируется с хостом `postgres`. Для запуска из IntelliJ IDEA
откройте корневой `pom.xml` как Maven-проект, выберите JDK 21 и задайте доступную
PostgreSQL через `DB_URL`, `DB_USER`, `DB_PASSWORD` в конфигурации запуска.
Spring автоматически не загружает `.env`.

## Тестирование

Нужны JDK 21 и доступ к Maven Central; для интеграционных тестов также Docker.

```bash
./mvnw test
./mvnw clean verify
```

`test` запускает модульные тесты, включая Mockito. `verify` дополнительно
выполняет интеграционные тесты через Maven Failsafe на временной PostgreSQL
из Testcontainers. База Compose не используется. Проверяются API, FEFO,
формулы, валидация, конкурентные операции и откат транзакций.

Spotless проверяет форматирование, SpotBugs — потенциальные ошибки,
Enforcer — версии инструментов. Форматирование: `./mvnw spotless:apply`.
Отчёты находятся в `target/surefire-reports`, `target/failsafe-reports`
и `target/site/jacoco/index.html`. GitHub Actions выполняет `verify`
при push и pull request.

## Ограничения

- Реализован REST API; пользовательский интерфейс и чат отсутствуют.
- Справочники заполняются начальным набором; отдельного CRUD и импорта нет.
- Параметры закупки и поставки передаются в запросе. Реестра заказов,
  автоматического размещения закупок и сохранения истории прогнозов нет.
- Сезонность, бюджетный лимит, категории и экспорт не реализованы.
- Операции записываются хронологически; произвольный исторический срез
  остатков не поддерживается.
- API без авторизации опубликован только на localhost. Нагрузочные пределы
  и качество прогноза на реальных данных не измерялись.

в обсуждении решений и code review.

готова обсудить с командой.
